# Review of the Clor R&D research (`/Users/suresh/Desktop/Clor R&D`, documents 01–10)

These are the points where the research conflicts with the code that exists, or would cause harm if applied as written. The research documents are not edited; corrections live here and in `DECISION_LOG.md`.

| # | Research says | Code reality | Recommendation |
|---|---|---|---|
| R-1 | `account_id` is the root isolation key; every product table carries `account_id` plus `company_id`, and RLS checks both (02 §1, §6, §7). | Every product table carries `orgId`. RLS checks `clor.org_id` on 169 tables, and `accountId` is derived from the org (ADR-001). CA delegation is granted per company, so the company is the real data boundary. | Keep `orgId` as the RLS key. Do not add `account_id` to roughly 170 tables: it is redundant (an org never changes account) and expensive. Account-keyed platform tables (`Subscription`, `User`, `Session` …) rely on application checks. Add an account-level policy only where a table holds rows from many accounts that request paths read. |
| R-2 | The example policy casts `NULLIF(current_setting(...), '')::uuid` (02 §7). | IDs are cuid strings, so `::uuid` raises an error on every row. | Compare text: `"orgId" = current_setting('clor.org_id', true)`. |
| R-3 | Use UUIDv7 identifiers (02 §1). | Every table uses cuid, and many IDs are already in customer exports and URLs. | Keep cuid. Opaque and stable is the property that matters. Human-facing codes stay separate (`Org.code`, as Zoho's org number). |
| R-4 | "No selected scope means no company data" (02 §7). | **Correct, and the code violates it.** Every policy passes all rows when no org is set (A-35). | Adopt it: fail-closed policies plus an explicit `BYPASSRLS` maintenance role for global jobs. This is the most important point in the research. |
| R-5 | Documents are private R2 objects with signed URLs (01 §3, 08 §2). | There is no object storage. Files are bytea in Postgres, served as JSON data URLs behind org checks (A-42). | Today's design is safe at pilot scale. Treat R2 as a later migration and don't record it as existing. Note that database size and backup time grow with photos. |
| R-6 | A separate Attendance database (01 §3, diagrams). | Attendance tables live in the People database. | Keep them there. Splitting adds cross-store integrity problems (A-39) for no isolation gain. |
| R-7 | "Durable background workers and outbox" (01 §3). | Thirteen `setInterval` jobs run inside each API replica on Cloud Run, with a fail-open lease (A-43..A-48). | Agreed target. Concrete path: a worker entrypoint triggered by Cloud Scheduler, a lease with a fencing token, and a `job_run` table. Interim: make the lease fail closed and add in-process guards. |
| R-8 | Cross-subdomain sign-in via authorization code + PKCE; don't share cookies across `.clor.in` (03 §2). | The refresh cookie is host-only on the API, path `/api/auth`, SameSite=strict. Product hosts get the session through the API. | The current design already satisfies the intent. No rebuild needed. The real cross-subdomain gap is the **company** not travelling between hosts (A-25), which is GAP-014. |
| R-9 | "Different tabs must bind each API call to an independently validated context" (03 §2, AC-11). | The org is per tab, but branch and warehouse are shared across tabs (A-23). | Agreed. GAP-014 adds `/o/<CODE>/` URLs and per-tab branch/warehouse state. |
| R-10 | Clor Platform Operator is an internal role, separate from customers (03 §4, AC-05). | The operator is an ordinary customer `User` listed in an env var, with no step-up or audit (A-17). | Agreed. Near term: require TOTP-in-session plus step-up plus audit. Later: a separate operator realm and audience. |
| R-11 | Maker/checker on pay runs, payments and leave (03 §7). | Research is right and **the gap is larger than the research assumed**: seven paths allow self-approval (A-13). | Add a shared `assertNotMaker` guard and status-guarded updates. |
| R-12 | Invitations are single-use, time-limited tokens (03 §2). | Adding a user attaches to any existing account with that email, verified or not (A-02). | Agreed, and urgent: refuse to attach to unverified users now; add accept-invite tokens next. |
| R-13 | Timelines: three to five months (09 §4). | A large share of the foundation already exists: global identity, memberships, RLS on every org table, SSO/SCIM, subscriptions. | The remaining work is hardening, not building from scratch. The checklist here is the sequenced plan. |
| R-14 | Account owner, CA engagement and Workforce Core are new tables (02 §3, 05). | They do not exist yet (GAP-005, GAP-006 — ADR-004/005 PROPOSED). | Unchanged. Do them after the P1 hardening batch, because they build on the authorization fixes. |

Research items that need **live** evidence and cannot be closed from source: OPS-01 restore drill, OPS-07 incident drill, Gate F legal review, and the CERT-In/DPDP operational items.
